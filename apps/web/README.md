# Форма — frontend

React + TypeScript, сборка Vite. Из корня репозитория: `npm ci`, затем `npm run dev`.
Интерфейс: http://127.0.0.1:5173, API: http://127.0.0.1:4000.
`npm run build` собирает оба приложения, `npm run test:web` проверяет frontend.
Архитектура и проверенные сценарии — в [README решения](../../README.md#решение).

## Структура интерфейса

`components/FullscreenMenu/` — отдельная папка меню с публичным `index.ts`.
Основной компонент соединяет `MenuTrigger` и `MenuPanel`; панель собирает
`MenuHeader`, `MenuNavigation`, `MenuStory` и `MenuFooter`. Пункт навигации и
иконка выделены отдельно. `useFullscreenMenu` отвечает за анимацию, отложенный
переход, блокировку прокрутки и возврат фокуса. Типы находятся рядом со своими
компонентами; общий SCSS Module сохраняет оформление без лишних DOM-обёрток.

Компоненты, утилиты, классы и их методы сопровождаются коротким JSDoc на русском:
назначение и важные условия работы, без пересказа сигнатуры и очевидных операций.

Обработчики событий и другие callback-пропсы JSX вынесены в именованные функции.
Для элементов списков функции привязывают нужный идентификатор, а типы обработчиков
переиспользуются из `*.types.ts`. Проверка структуры не допускает inline-функций
в JSX-атрибутах.

Объектные типы и именованные объявления вынесены в соседние `*.types.ts`.
Пропсы названы по компонентам, например `FullscreenMenuProps` и `ProductCardProps`.
Общие пропсы состояния переиспользуются через
`components/shared.types.ts`; компоненты и модели импортируют типы через `import type`.
Проверка структуры исходников запрещает возвращать объявления типов и анонимные
объектные аннотации в файлы с логикой.

- `src/App.tsx` собирает каркас страницы; `ShopContent` показывает загрузку или `Outlet`, а `src/hooks/useCheckoutLifecycle.ts` управляет восстановлением приложения и подпиской на маршрутизатор.
- `src/components/` содержит отдельные карточки товаров и заказов, блок оформления и переиспользуемые поля адреса и варианты выбора.
- `src/constants/` содержит статические тексты интерфейса, ошибки, доступные подписи и конфигурации. `checkout-form.ts` задаёт поля адреса и варианты оплаты, `menu.ts` — ссылки меню, `payment.ts` — тексты состояний оплаты.
- Тексты с параметрами оформлены функциями. Названия товаров, номера заказов и другие данные API остаются данными, а не копируются в словарь.

Новые надписи добавляйте в соответствующий файл `constants`, настройки повторяемых элементов — в именованные объекты вне JSX. Тест `source-structure.test.ts` проверяет отсутствие русских строк вне констант и массивов конфигурации, создаваемых непосредственно перед `.map()` внутри JSX.

Поле телефона использует `react-phone-number-input/input`: форматирование при вводе,
российский формат по умолчанию и международные номера с `+`. В модель и API передаётся
E.164 без пробелов. Неполные номера проверяются через `isPossiblePhoneNumber`.
DOM-тесты проверяют набор, вставку, очистку и редактирование цифр в середине номера.

## Библиотеки интерфейса и проверки

- Стили — `global.scss` и `*.module.scss`. Vite использует `sass`; вложенность ограничена двумя уровнями. CSS Modules, `composes`, camelCase-классы и `classnames` сохранены. Стили сторонних библиотек не переписываются.
- Иконки — именованные импорты из `lucide-react`; декоративные иконки скрыты от скринридера, у кнопок остаются доступные подписи. Авторские иллюстрации товаров остаются SVG.
- `components/CheckoutForm/` содержит секции контактов, доставки и оплаты. `useCheckoutForm` управляет полями через React Hook Form (`onTouched`), сохраняет независимые снимки черновика и связывает серверные ошибки с полями. `form-resolver.ts` переиспользует существующую проверку `validate`, согласованную с API; Zod не добавлен.
- `src/router.tsx` задаёт маршруты через `createHashRouter`: `#/`, `#/checkout`, `#/orders`, `#/orders/:orderId`. Старый `#/order` поддерживается. React Router управляет историей и параметрами, модель не вызывает `pushState` и `replaceState`. `createHashRouter` выбран для подключения навигации модели вне React, сохраняя hash-ссылки.
- ESLint проверяет TypeScript, React Hooks, неиспользуемые переменные, шаблонные строки и пустые строки между объявлениями. Stylelint проверяет SCSS, camelCase и глубину вложенности; `composes` разрешён. Prettier остаётся форматтером.

Из корня: `npm run lint -w @checkout/web`; отдельно — `lint:code` и `lint:styles`.
Все конфигурации находятся в `apps/web`. Корневой `package-lock.json` обновлён только для фиксации зависимостей workspace.

## Модель и общие утилиты

`src/lib/http.ts` централизует отправку запросов, заголовки сессии, разбор ответов
и ошибок; `src/api.ts` описывает типизированные операции. Модель
`src/model/checkout.ts` управляет формой, расчётом, заказами и оплатой, а общий
`poll` в `src/lib/async.ts` — ожиданием и отменой опроса. UI получает готовые данные.
Правила формы и состояния оплаты вынесены в `model/form.ts` и `payment-state.ts`.

Реальный участок обработки данных — количество товара в каталоге. `Catalog`
создаёт `Map<productId, quantity>` за один проход по C позициям корзины только при
изменении ссылки на корзину (`useMemo`). Каждая из P карточек делает O(1)-поиск:
итого O(C + P), один Map на изменение корзины, без отдельного `find` по корзине
для каждой карточки и промежуточных массивов. При обновлении других состояний
индекс переиспользуется. Данные — плотные массивы объектов из JSON; дырки не
создаются, оптимизации движка для массивов одних чисел здесь не предполагаются.

## Проверки отказоустойчивости

Состояния оплаты определены в `src/model/payment-state.ts`: `pending` означает выбор
тестовой карты, а не обработку. Опрос платежа идёт только в `processing`.
После `succeeded` интерфейс остаётся в `verifying_order`, пока контрольный GET заказа
не подтвердит оплату. Это работает и после перезагрузки. Повторное открытие формы
для уже ожидающего/обрабатываемого платежа заблокировано в модели, не только кнопкой.

Если контрольный GET заказа после начала обработки упал, кнопка повтора
возобновляет проверку заказа и опрос платежа, не отправляя симуляцию повторно.

Тело и ключ неопределённого POST сохраняются до отправки в `localStorage`, поэтому
восстановление переживает и перезагрузку, и закрытие браузера. Повтор не создаёт
новый заказ или платёж; отказ и отмена позволяют начать новую попытку для того же
заказа. Номер карты и CVC не собираются: используются только тестовые сценарии API.

`npm run test:web` проверяет в том числе потерянные ответы, перезагрузку,
двойные действия, отмену/отказ/успех и задержку подтверждения заказа.

Для короткого E2E-набора из корня:

```sh
npx playwright install chromium
npm run test:e2e
```

Три сценария запускаются на ширинах 390 и 1280: оплата с отменой/отказом/reload,
потерянный ответ создания заказа и точный повтор, браузерная история и оформление
с клавиатуры. Серверы используют отдельные порты 4100/5273 и API в памяти;
пользовательская `.data` не затрагивается. Playwright запускается отдельно от
`npm run check`; список сценариев: `npm run test:e2e -- --list`.

Проверка только frontend (из корня, после установки зависимостей и первоначальной
сборки готового API/контрактов): `npm run build -w @checkout/web` и
`npm run test:web`. Эти команды не пересобирают backend.

## Ограничения

- Это тестовая оплата без настоящих карточных данных и списания денег.
- Сессия и неопределённые операции восстанавливаются через localStorage;
  очистка хранилища браузера удаляет локальные данные восстановления.
- История заказов ограничена текущей гостевой сессией. Регистрация, личный
  кабинет и админка не входят в задание.
