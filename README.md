# Тестовое задание для фронтенд-разработчика

## Решение

**Форма** — адаптивный магазин с каталогом, серверной корзиной, оформлением и тестовой оплатой.
React 19, TypeScript, Vite. Стили и иллюстрации локальные; внешние сервисы не используются.
Бэкенд и API-контракты сохранены без изменений.

### Запуск решения

Из корня репозитория, Node.js 24.x и npm 11.x:

```sh
npm ci
npm run dev
```

Одна команда запускает API на http://127.0.0.1:4000 и frontend на http://127.0.0.1:5173.
Остановка — Ctrl+C. Сессию приложение создаёт самостоятельно.

```sh
npm run dev:api       # только API
npm run dev:web       # только frontend
npm run build         # сборка contracts, API и frontend
npm run test:web      # frontend: транспорт и сценарии с настоящим API в памяти
npm run check         # форматирование, сборка, все тесты, проверка OpenAPI
npm run smoke         # HTTP-проверка при запущенном API
```

Vite проксирует `/api` в локальный API. Для другого адреса задайте
`VITE_API_URL=http://localhost:4100` при запуске/сборке frontend
либо измените proxy в `apps/web/vite.config.ts`.
Для просмотра сборки: `npm start` и в другом терминале
`npm run preview -w @checkout/web`.

### Устройство

- `src/lib/http.ts`: подготовка заголовков и тела, отправка, разбор JSON/пустых ответов,
  единая `ApiError` с кодом, статусом, полями и requestId. Адаптер `envelope` извлекает
  `data`. Endpoint-функции в `src/api.ts` возвращают типизированные данные; компоненты
  не работают с `Response`, `fetch` или HTTP-разбором.
- `src/lib/async.ts`: подписки состояния и последовательный polling с AbortSignal.
  Новый запрос опроса начинается после завершения предыдущего и паузы; отменённый
  ответ не попадает в состояние.
- `src/model/checkout.ts`: корзина, расчёт, заказ, попытки оплаты и восстановление.
  Общий `run` управляет блокировкой повторного действия, ожиданием и нормализованной ошибкой.
  Поля, выбор доставки и оплаты отделены от серверных сущностей.
- `src/model/form.ts`: общая валидация контактов/доставки и форматирование копеек.
  `Field` связывает подпись и ошибку с полем, `ErrorNotice` показывает разобранную ошибку.
- Компоненты получают состояние через `useSyncExternalStore`. Транспорт и модель
  можно проверять без DOM; тесты модели используют неизменённый Fastify API через inject.

Изменение корзины последовательно отправляет абсолютное количество/удаление, затем читает
серверную корзину. Итоги не рассчитываются повторно на клиенте. Изменение доставки
инвалидирует quote сразу и после 400 мс отправляет новый расчёт для валидного адреса.
Предыдущий запрос отменяется, а счётчик версии защищает от запоздавших ответов.
Контактные поля не запускают перерасчёт доставки.

Заказ создаётся по свежему quote. Сетевой сбой сохраняет **точное тело и ключ** в
localStorage до разрешения неоднозначности; повтор и перезагрузка не создают второй заказ.
Аналогично восстанавливается создание попытки оплаты. Выбранный сценарий имитации
сохраняется отдельно и не меняется при повторе потерянного запроса.
Отказ/отмена допускают новую попытку для прежнего orderId.
При устаревшем расчёте/версии корзины данные обновляются, форма сохраняется,
изменённая сумма требует нового подтверждения пользователя.

Успех для карты — только `paid / succeeded` из GET заказа. Для наличных —
`confirmed / unpaid`, без создания платежа. Сессия, форма, текущий экран, заказ
и неоднозначные операции восстанавливаются после перезагрузки.
Polling работает только на экране текущего заказа и останавливается при выходе/завершении.

### Обработка данных и стоимость

`Catalog` строит индекс количества товаров по productId одним проходом по корзине
за O(C), выделяя один Map. Индекс пересоздаётся только при новой серверной корзине
(`useMemo([cart])`), не при изменении контактов. Во время рендера P товаров проверяются
через Map.get за O(1) на товар: суммарно O(P + C), без `find` внутри обхода каталога.
`CartSummary` так же переиспользует индекс остатков, построенный при обновлении каталога.
Массивы плотные; `delete array[i]`, копирование растущего аккумулятора и цепочки
`map().filter()` в этих путях отсутствуют.

### Проверки и границы

Автотесты: пустые 204/304, malformed JSON, сетевые/HTTP/полевые ошибки,
отмена и завершение polling, основной сценарий картой, отказ → отмена → успешный повтор,
наличные, остатки, пустая корзина, валидация, двойное оформление, потерянные ответы
заказа/платежа/имитации, конфликт корзины, просроченный quote, восстановление processing
и защита от устаревшего расчёта. Все backend-тесты остаются в общем `npm run check`.

Ручная проверка в браузере: каталог, добавление товара, оформление с курьером,
тестовая оплата и повтор, восстановление после перезагрузки; адаптивные экраны 1280 и 390 px.
Данные для проверки: buyer@example.test, +79990000000, г. Учебный, ул. Примерная, дом 10.

Ограничения: локальное учебное приложение, без реальных платежей, регистрации и истории
всех заказов в UI. Токен хранится в localStorage согласно локальному сценарию задания;
между вкладками нет активной синхронизации — конфликты разрешаются через сервер.
Для новой гостевой сессии после сброса API предусмотрена кнопка восстановления.
Если браузер запрещает localStorage, приложение показывает ошибку перед созданием
неоднозначной операции. Деплой не выполнялся.

## Запуск

Потребуются Node.js 24.x и npm 11.x. Отдельная база данных и ключи внешних сервисов не нужны.

```sh
git clone https://github.com/instatdigital/frontend-checkout-challenge.git
cd frontend-checkout-challenge
npm ci
npm run dev
```

Swagger: [http://localhost:4000/docs/](http://localhost:4000/docs/). Спецификация: [http://localhost:4000/openapi.json](http://localhost:4000/openapi.json) или [файл в репозитории](docs/openapi.json).

В Swagger выполните `POST /api/sessions` с телом `{}`. Скопируйте `data.token` в **Authorize**, без слова `Bearer`.

## Структура

```text
apps/api/             бэкенд
apps/web/             ваш фронтенд
packages/contracts/   схемы API и типы TypeScript
docs/                 задание и документация
scripts/              проверки
```

Проект использует npm workspaces. Frontend — `@checkout/web`; `npm run dev` запускает API и frontend вместе.

Стили интерфейса подключаются через CSS Modules (`*.module.css`), условные классы — через `classnames`.
Общие стили приложения находятся в `apps/web/src/App.module.css`, стили меню и счётчика — рядом с компонентами.
В `apps/web/src/global.css` остаются базовые стили HTML-элементов и настройки страницы.

## Проверки

```sh
npm run check       # форматирование, сборка, тесты и OpenAPI
npm run build
npm start           # запуск собранного бэкенда
```

При работающем API в другом терминале выполните `npm run smoke`. Эта команда проверяет покупку, отказ карты, отмену и повтор оплаты по HTTP.

## Настройки

Адрес по умолчанию — `127.0.0.1:4000`. Если порт занят, скопируйте `.env.example` в `.env` и измените `PORT`. Для проверки другого порта передайте `BASE_URL`, например `BASE_URL=http://localhost:4100 npm run smoke`.

Фронтенд может работать на любом HTTP-порту `localhost`, `127.0.0.1` или `[::1]`. Другие разрешённые адреса задаются в `CORS_ORIGINS`. Авторизация передаётся заголовком; cookies и `credentials: include` не нужны.

Данные сохраняются в `.data/store.json`. Запускайте один экземпляр API на один файл. Для сброса остановите сервер и выполните `npm run data:reset`; затем создайте новую сессию. Если меняли `DATA_FILE`, свой файл удалите вручную при остановленном сервере.

Товары и адреса вымышленные. Остаток ограничивает количество в одной корзине и не уменьшается у других покупателей. Для получателя используйте тестовые контакты, например `buyer@example.test`. Вместо ввода номера карты интерфейс должен предлагать тестовые карты из API.

Корневые команды сборки и тестов проверяют API и frontend. Зависимости закреплены в корневом `package-lock.json`, типы API импортируются из `packages/contracts`.
